# 발표 논리 기준 (storyline)

장표를 그리기 전에 이야기를 먼저 세운다. 이 문서의 규칙 중 기계로 잴 수 있는 것은
`scripts/story.py`가 그대로 검사한다(`deck.py check`). 검사를 통과해도 "제목만 이어 읽으면
이야기가 되는가"는 사람이 확인한다.

## 1. 먼저 정하는 네 가지

| 항목 | deck.json | 기준 |
|---|---|---|
| 한 문장 주장 | `meta.thesis` | 발표 전체가 이 문장 하나로 모인다. 70자 안. 없으면 빌드하지 않는다 |
| 청중 | `meta.audience` | 무엇을 이미 아는지가 배경 설명의 길이를 정한다 |
| 유형 | `meta.type` | `talk`(컨퍼런스 발표) · `share`(사내 공유·세미나) · `briefing`(보고·브리핑) |
| 시간 | `meta.minutes` | 장 수의 기준. 아래 표 |

| 유형 | 분당 장 수 | 예: 20분 |
|---|---|---|
| talk | 0.8–1.3 | 16–26장 |
| share | 0.7–1.2 | 14–24장 |
| briefing | 0.5–1.0 | 10분이면 5–10장 |

## 2. 목차 구성: 유형별 골격

목차 장은 주제 목록이 아니라 **이야기가 움직이는 단계의 지도**다. 단계 이름은 명사가 아니라
움직임으로 쓴다("문제", "해결" 대신 "어디서 틀리나", "모델을 바꿔 봤다"). 같은 지도가 구간 표지와
마무리에서 다시 나와서, 청중이 지금 어디쯤인지 놓치지 않는다.

### talk (컨퍼런스 발표)

```
1  표지              cover
2  지도 (3–5단계)     map        ← 목차. 마지막 단계가 이 발표의 제안
   ┌ 구간 표지        section    ← 지도를 다시 보여 주고 이번 단계만 강조
   │ 본문 2–6장       context · claim · evidence
   └ (단계 수만큼 반복)
   반론 2장 이상      counter    ← 제안보다 앞에. 불리한 근거를 먼저
   입장 1장           stance     ← 반론을 본 뒤의 내 입장. Q&A 형식이 잘 맞는다
   제안 → 근거 → 예시 → 적용     proposal · evidence(own) · example · action
N  마무리            close      ← 지도를 다시 보여 주고 마지막 단계를 강조 + 한 문장
```

- 배경이 발표를 삼키지 않게 한다. 제안·예시·적용·직접 측정 장이 본문의 **40% 이상**이 되게 잡는다(35% 아래면 경고).
- 제안 구간의 근거는 직접 만든 결과가 가장 강하다. 남의 결과만으로 내 제안을 받치면 가장 먼저 질문받는다.

### share (사내 공유·기술 세미나)

`표지 → 지도 → 문제 → 시도 → 결과 → 배운 점 → 다음 할 일 → 마무리`. 반론은 1장 이상.
"우리가 틀렸던 것"을 숨기지 않는 것이 공유 발표의 가치다.

### briefing (보고·브리핑)

```
1  표지
2  결론 먼저          conclusion  ← 숫자 하나 + 정할 것. 제목 없는 statement 장
3  근거 2–4장         evidence
   위험·반론 1장      counter
N  결정 요청          ask         ← 정해야 할 것을 카드로. 마지막 장
```

지도는 없다. 듣는 사람은 결론과 정할 것만 기억한다.

## 3. 장 하나의 구성

| 자리 | deck.json | 규칙 |
|---|---|---|
| 제목 | `title` | **주장이나 질문**. 한 줄(28pt에서 한글 약 30자). "개요·배경·현황·결론" 같은 주제 이름은 오류 |
| 부제 | `lead` | 왜 중요한지 한 문장, 한 줄(16pt에서 약 52자). 개조식으로 끝낸다(~함, ~됨, ~중) |
| 근거 | `visual` · `side` · `columns` … | 중심 근거는 하나. 그림·차트·인용·표 중 하나가 주인공 |
| 큰 숫자 | `side[].value` · `items[].value` | 한 장에 하나가 기본. 전후 비교가 가장 잘 읽힌다(`61% → 81%`). 아래에 무엇의 숫자인지 한 줄 |
| 출처 | `source` | 숫자·차트·표가 있으면 필수 |
| 이어받는 질문 | `answers` | 앞 장이 남긴 어떤 질문에 답하는지. 발표자 노트의 "넘어가는 말"이 된다 |

한 장 = 한 메시지. 근거가 둘 이상 필요하면 장을 나눈다.

## 4. 흐름 규칙

1. **질문으로 잇는다.** 장마다 `answers`를 적는다. 흐름이 꺾이는 곳은 질문 자체를 제목으로 둔다
   ("그럼 더 큰 모델을 쓰면 되지 않나?"). 입장 장의 마지막 줄(`bridge`)은 다음 구간의 질문이다.
2. **제안 전에 반론을 꺼낸다.** 내 주장에 불리한 수치를 먼저 보여 주고, 그다음에 입장을 밝힌다.
   과장한다는 인상이 사라진다. 제안 앞에 반론이 0장이면 오류다.
3. **앞에서 꺼낸 것을 뒤에서 다시 쓴다.** 숫자·단어·그림을 앞에서 꺼내고(`plant`) 뒤에서 다시 쓴다(`payoff`).
   talk는 2짝 이상(권장 3짝). 지도 → 마무리는 기본으로 한 짝이다. 이렇게 이어진 발표가 하나의 이야기로 읽힌다.
4. **용어는 7개 안쪽.** 새 용어는 `terms`에 적고, 처음 나오는 장에 `defines`로 정의한다. 지도에 없는 개념을 본문에서 늘리지 않는다.
5. **내 주장과 남의 결과를 나눈다.** `tags`로 표시하면 장 위쪽에 작은 표시가 붙는다.
   `concept`(우리 제안) · `example`(설명용 예시) · `limit`(한계) · `own`(직접 측정, 표시 없이 출처 줄로).

## 5. 출처 규칙

- 형식: `출처: arXiv 2401.15884 · cursor.com/blog/… (2025.11) · 조회 2026.10.26`
- 직접 잰 값: `직접 측정 · 2027.02 · 질문 300개`
- 스크린샷·스타 수처럼 바뀌는 값: 캡처 날짜를 적는다.
- 작은 수에서 나온 배수는 원래 수를 함께 적는다(`6→107편`, `×17.8`).
- 출처가 없는 숫자는 쓰지 않는다. 숫자를 새로 만들지 않는다. 가상의 예시 수치는 출처 줄에 `설명용 가상 데이터`라고 적는다.

## 6. 말투와 표기

- 장표 문장은 개조식, 마침표 없이: "모델을 키워도 3점 올랐음".
- 청중에게 직접 하는 말(Q&A의 답, 마지막 문장)만 "~입니다".
- 영문·숫자 뒤 조사는 붙여 쓴다: `RAG의`, `Claude Code는`, `300개를`. 괄호 안쪽과 문장부호 앞에 공백을 넣지 않는다. 검사기가 막는다.
- 꾸밈말 대신 숫자: "획기적으로 개선" → "61%에서 81%로".
- `**굵게**`, `==강조색==` 두 가지 표시만 쓴다. 한 문장에 강조는 한 군데.

## 7. 발표자 노트

- `notes`: 이 장에서 말할 것 1–3문장. 손으로 짚을 곳, 청중에게 던질 질문.
- 다음 장의 `answers`가 "넘어가는 말"로 자동으로 붙는다.
- 리허설 전에 구간별 시간을 정한다: 지도 단계마다 몇 분인지 `notes` 첫 줄에 적어 둔다.

## 8. 사람이 확인할 것 (검사기가 못 보는 것)

- [ ] `outline`의 제목 열만 위에서 아래로 읽으면 하나의 이야기가 되는가
- [ ] 첫 3장 안에 청중이 "이 발표에서 무엇을 얻는지" 알 수 있는가
- [ ] 반론이 허수아비가 아닌가. 그 분야 사람이 실제로 할 반론인가
- [ ] 마무리 문장이 `meta.thesis`와 같은 말을 하는가
- [ ] 큰 숫자마다 "그래서 뭐?"에 답하는 한 줄이 있는가
